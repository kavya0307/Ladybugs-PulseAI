# PROMPTS.md

This file documents the AI-assisted workflow used to build **Autonomous AI Creator**
(Ladybugs-PulseAI) for the "Autonomous AI Creator" hackathon challenge.

Two AI tools were used, at two different stages:

- **Antigravity** — initial scaffolding of the entire application, built by providing
  the hackathon problem statement directly.
- **Claude** — code review, live testing of both the local and deployed app, targeted
  bug fixes, and a final upgrade to add real LLM-powered editorial judgment and
  post writing.

---

## 1. Initial Build — Antigravity

The first working version of the app (Express API, autonomous agent pipeline, and
React dashboard) was generated by Antigravity from a single input: the full
"Autonomous AI Creator" hackathon problem statement (minimum requirements, API
contract, and evaluation criteria), pasted in directly with no additional prompt
engineering.

From that one input, Antigravity produced:

- `server/agent/discovery.mjs` — live topic discovery from Hacker News, arXiv, and Dev.to
- `server/agent/editorial.mjs` — keyword-based topic scoring and rejection logic
- `server/agent/persona.mjs` — five preset personas (Ada, Marcus, Elena, Kaelen, Soren)
- `server/agent/memory.mjs` — persistent post history and deduplication
- `server/agent/runner.mjs` — the autonomous background publishing loop
- `server/index.mjs` — the required `POST /api/agent/init` and `GET /api/agent/feed` endpoints
- `src/` — the full React dashboard (Feed Viewer, Editorial Audit Log, Memory Inspector,
  Persona Selector, API Console)

*We did not keep a turn-by-turn prompt log from this stage — the problem statement
itself was the only input, and Antigravity generated the scaffold in response.*

## 2. Review, Debugging & Fixes — Claude

After the initial build, Claude was used to review the codebase, run it locally and
against the live Render deployment, and implement specific fixes. The summary below
follows the actual sequence of requests made in that conversation.

### 2.1 Choosing the problem statement
> "which problem statement is worth of winning the hackathon"

Asked before development started, comparing this challenge against an alternative
hackathon track to decide which to build.

### 2.2 Understanding the requirements
> "all we are going to do is vibe code the whole hackathon. just explain me what are
> requirements for ai autonomous creator in detail and simple"

Used to get a plain-language breakdown of every minimum requirement and the exact
API contract before development/review began.

### 2.3 First code review
> "we have created this website but it was sent from my teammate and i cant open it.
> what i have to do to open the file. and please review the website and give
> recommendations for any changes or alternates. also explain each features and
> components for our understanding. rate the website out of 10 and do you think we
> will win?"

Claude unzipped the Antigravity-built project, explained how to run it
(`npm install`, `npm run server`), read through every backend and frontend file, and
ran it locally — calling `POST /api/agent/init` and `GET /api/agent/feed` directly.
This surfaced two key findings:
- **No LLM call anywhere in the codebase** — editorial judgment and post writing were
  both fully rule-based/templated, not AI-generated, despite the app being an "AI
  Creator."
- **A keyword-matching bug**: persona keywords in singular form (e.g. `"vulnerability"`)
  failed to match plural forms in discovered content (e.g. `"vulnerabilities"`),
  causing clearly on-topic candidates to be wrongly rejected. Reproduced live: 7 out
  of 7 candidates rejected for the Ada persona in one test cycle.

Initial rating: **6.5/10**.

### 2.4 Checking the live deployment
> "https://ladybugs-pulseai.onrender.com this is the finally deployed website. rate this one"

Claude's web-fetch tool could only retrieve the static HTML shell (the dashboard is a
client-rendered React app), so it could not verify live behavior directly and asked
for screenshots or direct API responses instead.

### 2.5 Live evidence via screenshots
Screenshots of the live dashboard were provided, showing: `AUTONOMOUS_RUNNING` daemon
status, a live `agentId`, published posts with expandable rationale and sources, and
a populated Editorial Audit Log (50/41 entries). This confirmed the deployment was
genuinely working end-to-end, not just locally.

Updated rating: **8/10**, with the LLM-integration gap and the keyword bug flagged as
the two things standing between "well-built" and "winning-tier."

### 2.6 Full spec compliance check
The complete hackathon problem statement was re-provided in full, with:
> "Actually this a hackathon project and this is the problem statement. so check that
> the website satisfy all the condition and then recommend me the upgrade that can be
> made to make this a winning agent model"

Claude checked the deployment against every individual requirement in the spec
(topic discovery, editorial judgment, persona consistency, memory, autonomous
publishing, rationale format, exact API contract, post ordering, ID uniqueness,
timestamp format, empty-state response) and flagged two real submission risks:
- A manually-clickable **"Run Autonomous Cycle"** button in the UI, which could make
  an evaluator question whether posts were genuinely autonomous or human-triggered.
- Whether switching personas in the UI created a new agent or silently mutated an
  existing one mid-run — checked directly in `persona.mjs`/`runner.mjs` and confirmed
  it always creates a **new** `agentId`, so this was not actually a bug.

### 2.7 Implementing the compliance fixes
> "yes!!!!!"

In response to Claude's offer to implement the two fixes directly, Claude made the
following changes, testing each one before and after:

1. **Gated the manual trigger** (`server/index.mjs`, `src/App.jsx`,
   `src/components/Header.jsx`) — `POST /api/agent/trigger` now returns `403` unless
   `ALLOW_MANUAL_TRIGGER=true` is explicitly set in the environment, and the frontend
   button only renders when a new `/api/agent/config` endpoint confirms it's enabled.
   Verified via curl: default request returns
   `{"error":"Manual triggering is disabled in this deployment."}`.

2. **Added restart persistence** (`server/index.mjs`) — on boot, the server now reads
   `store.json` and automatically resumes the autonomous publishing loop for any agent
   still marked `ACTIVE`, protecting against a Render redeploy or free-tier sleep/wake
   cycle silently freezing a running agent mid-evaluation. Verified by killing and
   restarting the local server twice; logs confirmed
   `[Boot] Rehydrating 1 previously-active agent(s): agent-ada-4khwf`, with the
   agent's post history and background loop both surviving the restart.

3. **Fixed the keyword-matching bug** (`server/agent/editorial.mjs`) — added a
   lightweight stemming/fuzzy-match function (`fuzzyKeywordMatch`) so persona keywords
   match simple plural/suffix variants in source text. Verified directly: the
   previously-rejected "Vector Database Indexing Vulnerabilities" topic now scores
   84/100 and is correctly approved.

The updated project was packaged and delivered as a downloadable zip.

### 2.8 Post-deploy verification
> "https://ladybugs-pulseai.onrender.com can you check the website now?? i just
> updated the website, now rate and check for any faults"

Again limited by tooling (no JS execution, no direct API access to the Render
domain), Claude asked for the same verification via the built-in API Console or
screenshots.

### 2.9 Confirming the fixes in production
Three screenshots of the redeployed live site were provided, confirming: the manual
trigger button no longer appears in the header (only "Refresh" remains), the
previously-failing "Indirect Prompt Injection via Vector Database Indexing
Vulnerabilities" post is now live in the production feed with full rationale and
source, and the built-in API Console's live `POST /api/agent/init` /
`GET /api/agent/feed` calls both return correctly shaped `200 OK` responses.

Updated rating: **9/10**.

### 2.10 Going for a perfect score
> "what can i improve in this for you to give this a 10 on 10. pls guide me through
> everything if there needs a change"

Claude gave a prioritized punch list: adding a real LLM call for editorial judgment
and post writing (the single highest-impact remaining gap), further hardening the
keyword pre-filter, making rejection rationale more visible in the feed itself,
solving the Render free-tier sleep risk definitively, and slowing the publish
cadence for a more deliberate 48-hour story.

### 2.11 Implementing the LLM upgrade
> "yes!!!!!" (confirming Claude should implement the compliance fixes directly)
> "okay help me with that to stand out"
> "yess i want to upgrade it"

Across these requests, Claude implemented real LLM-powered editorial judgment and
post writing:

- **New file `server/agent/llm.mjs`** — a shared Claude API client with
  `llmEvaluateCandidate()` (judges topics in the persona's actual voice and focus
  areas, not just keyword matching) and `llmWritePost()` (writes the post in-character).
  Both are designed to return `null` on any failure — bad key, network issue, timeout,
  malformed response — rather than throwing.
- **Updated `server/agent/editorial.mjs`** — the original keyword logic was preserved
  as `keywordEvaluateTopics()`, now used as both a cheap pre-filter (catching obvious
  spam/duplicates before spending an LLM call) and the guaranteed fallback path. The
  new `evaluateTopics()` sends surviving candidates to Claude for real reasoning,
  falling back to the keyword verdict for any candidate where the LLM call fails.
  `generatePost()` similarly tries the LLM writer first and falls back to the original
  template writer on failure.
- **Updated `runner.mjs` / `index.mjs`** — wired the now-async evaluation/writing
  functions through correctly, added `dotenv` support, and added a boot-time log line
  plus an `/api/agent/config` field reporting whether LLM mode is active.
- **UI update (`Header.jsx` / `App.jsx`)** — added a visible badge showing
  "AI-Powered Judgment" (purple) when a real API key is configured, or "Template Mode"
  (grey) when it isn't, so the judgment source is transparent to anyone viewing the
  dashboard.

This was tested directly rather than assumed to work:
- **No API key configured** — confirmed the app boots in template mode, cycles run
  normally, and posts publish exactly as before (regression-safe).
- **Invalid/expired API key** — confirmed all LLM calls fail with logged `401` errors,
  and the system automatically falls back to keyword scoring and template writing
  *without* crashing or skipping a cycle — a post still published successfully. This
  was the key robustness proof: even total LLM failure during the unattended judging
  window cannot produce an empty feed.
- Restart persistence and the keyword fuzzy-match fix were both re-verified after the
  LLM changes to confirm no regressions.

### 2.12 Final status check
> "just revisit the repo to check for its current status too"

Claude re-audited every prior fix directly in the code (grep-confirmed each one was
still present and wired correctly) and re-ran the full pipeline end-to-end one more
time — no-key path, restart/rehydration path, and feed-shape validation — before
handing off the final build.
